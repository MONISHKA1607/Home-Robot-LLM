# Writeup — Home Robot Language Control

## Approach

The model proposes one action at a time; the simulator executes it and returns a real `Result`; that result is fed back before the next action is proposed. I built four layers around that loop rather than trying to get everything right in the prompt alone:

1. **Tool awareness.** Before every LLM call, the transcript includes an "AVAILABLE ACTIONS RIGHT NOW" menu computed directly from the robot's actual state — what's sensed, what's held, what's unsafe. Legal actions are marked OK, impossible ones are marked BLOCKED with the reason, right next to each other. This doesn't replace validation, but it means the model reasons about "what can I do right now" explicitly at every step instead of inferring it from a wall of rules.
2. **Validator.** A code-level firewall between the LLM's proposal and the robot's actuators. Unknown skills, unsafe object categories, nonsense locations, and — after a bug I found mid-testing — placing an object back at the exact spot it was just picked up from, are all rejected here regardless of what the model decided. A prompt instruction is a suggestion; this is a hard rule.
3. **Failure classification.** Every failure is tagged (perception / execution / capability / safety / planning) instead of handled identically. A failed grasp is worth retrying; an unsensed object should prompt more exploration, not a retry; an out-of-scope request should just be declined.
4. **Mission trace.** Every step is logged as a structured record, with a short console-only report at the end (rooms visited, retries, failures by type, outcome). Never spoken to the person — purely for debugging.

I defaulted to Groq's free tier (`llama-3.3-70b-versatile`) since it's fast enough for an 8–14 step loop, but the provider is a single swappable function — Anthropic, Gemini, and local Ollama all work by changing one env var.

## Tradeoffs

The one I went back and forth on most: whether to hardcode a search order for objects (e.g. always check furniture — counters, tables, desks — before room anchors). I left it out. Doing that would mean quietly encoding assumptions tuned to the visible test set, and could burn steps on a hidden test where the assumption doesn't hold. Instead, the action menu *tags* each unvisited location by kind (furniture vs. room anchor) as pure information, and I shuffle presentation order per call so the model can't lean on `known_locations`' alphabetical ordering as an accidental search prior. The model still decides where to look, using the actual wording of the request.

The other real tradeoff was where to put the "don't place it back where you picked it up" rule. It started as a prompt instruction only. Testing showed that wasn't reliable enough — the model would occasionally place an object right back at the pickup location and then wander off, reporting success it hadn't earned. I moved the check into the validator as a hard block, but a hard block that ends the task outright made recovery *worse*, not better — the robot would still be holding the object with nothing left to do. So the block became a bounded, in-loop correction: reject the place, tell the model why as an observation, let it try again. That's the same "validate, don't just prompt" philosophy applied one level deeper, and it's the fix I'm most confident actually mattered.

## What breaks, and what I'd do differently

The clearest remaining gap, visible across most test runs: the model sometimes treats a successful delivery as a reason to keep exploring rather than call `done`, and can burn the step budget wandering into locations unrelated to the request. When that happens, the final spoken line ("this is taking longer than it should") sounds like failure even on a run where the object was actually delivered correctly. That's a reporting problem more than a behavior problem — the simulator-level outcome and the person-facing message can diverge — and with more time I'd close that gap explicitly: detect a successful delivery mid-loop and nudge the model toward `done` immediately, rather than relying on rule-following alone.

I'd also raise `MAX_STEPS` modestly (from 10 to ~14). A chunk of wasted steps on smaller models comes from correctable planning missteps (retrying `place` with the wrong argument) rather than genuine confusion, and a tighter budget punishes that disproportionately.

Longer term, the two things I deliberately left out — a full state machine and a confidence-scored world memory — are real for production robotics stacks, but would have buried this assignment's actual scoring criteria (grounding, safety, ambiguity, recovery) under indirection that doesn't change behavior here. The robot object already *is* the world state; wrapping it further wasn't worth the complexity for what's being tested.
